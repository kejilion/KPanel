## 原因假设

- 待验证根因：scoped 的全区间覆盖口径与单功能前置审计矛盾，积压在稳定版集中补审；源码发现与后续验证没有独立状态和统一收益口径。
- 可能的替代解释：复杂产品变更本来需要更多审查，平台/记录返工而非猎取本身导致长耗时；新线索价值尚未得到验证。
- 能证伪本假设的结果：分批后仍重复检查已审且未变的单元，或在相同规模和工具环境下成本不降、已验证问题的关闭率下降。
- 是否涉及脚本/权限/兼容契约：不修改产品和脚本契约；只修正审计覆盖声明、运行方法与成本/收益记录。

## 产品原则与核心思想对齐

- 对业务真源和双端互通的影响：无产品行为变化，不借审计限制合法管理员能力。
- 对轻量控制面的影响：无新常驻服务；复用既有 metadata、账本、修复追踪和覆盖检查。
- 对安全与稳定的影响：维持 14/30 天阈值、稳定版阻断、独立验证、固定 pin、无 OS 沙箱不执行目标等底线。
- 不应引入的复杂度或第二真源：不新建全局数据库；成本与风险处置摘要附在 run metadata，原始证据保持仓库外。

## 最小改动方案

- 预计修改文件或唯一入口：覆盖检查支持可选 reviewed_commits；完整运行旧语义兼容，显式列表严格验证；其余由现有 5.4 和 workflow 定义执行与证据要求。
- 新增或调整的自动门禁：复用现有覆盖 --validate/--require，不增产品或 CI 门禁；分批只消掉声明且核验过的提交。
- 迁移、兼容和失败恢复：历史 run 不改写；带列表的 complete scoped 只计列表，新分批统一 scope_complete=false 防止旧入口误计整段；旧完整区间语义保留；partial/interrupted 保存可复用证据，未审单元保持 pending。
- 防止指标投机或规则自我弱化的约束：覆盖 complete 与风险关闭独立，预算耗尽不宣称 clean，去重有效收益必须带独立复核和修复证据。
