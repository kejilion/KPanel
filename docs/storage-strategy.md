# KPanel 持久化与数据存储策略

- 版本：2026-07-31
- 状态：长期强制策略

本策略服从仓库根目录的 [`PROJECT_RULES.md`](../PROJECT_RULES.md)，用于指导 KPanel
根据产品需求选择 JSON、JSONL、SQLite 或 PostgreSQL。存储技术服务于业务，不预设
“全部 JSON”或“全面数据库化”路线。

## 1. 产品前提

1. Docker Engine、Nginx、init/service 状态、系统文件、`/home/web` 和 `kejilion.sh` 产物是业务
   真实状态；任何数据库都不得成为这些资源的第二套事实来源。
2. Panel 只持久化面板自身数据，例如账户、Session、审计、任务索引、通知、计划和必要缓存。
3. Agent 的高权限执行状态、完成凭据和有界日志保持独立，不能为了统一查询而扩大 Panel
   容器的宿主机权限。
4. 每一种存储必须有容量、条目数、保留期、清理、备份、恢复和损坏处理规则。
5. 当前版本继续使用已有 JSON/JSONL 实现；本策略保留 SQLite 的产品演进能力，不增加当前
   安装、运行或升级依赖。
6. 交互终端的 PTY 原始输出、输入流和会话映射只允许保存在有界内存中，不写入 JSON、JSONL、
   SQLite、审计或终端回放；进程退出、闲置回收或服务重启即清除。
   管理员命令历史是唯一独立例外：只保存终端页面识别的 shell 命令与显式批量命令，不保存按键流、
   常见密码提示及受支持的程序提示符输入、PTY 输出或回放。全 Panel 共享一份有界 JSON，最多 200 条去重命令、单条
   8 KiB、磁盘文件最多 4 MiB；按最近执行顺序淘汰，保留至淘汰或管理员删除/清空，不另设时间保留期。
   目录 0700、文件 0600，原子替换；写入失败不无限重试，损坏时停用并保留原件，仅显式清空可恢复。
   命令参数可能含有秘密，界面须提示本机保存及空格前缀排除方式；不把识别 shell 提示符当作完整
   敏感内容检测；任意自定义提示符无法可靠区分 shell 与程序，敏感操作须使用空格排除或事后清空。历史正文不得进入审计、面板备份或日志，不作为宿主 shell 历史真源；回滚旧版不读取
   此文件且不迁移、不删除，管理员可在新版清空。协议、路径、请求限额及验收以
   [多主机终端](multi-host-terminal.md) 和 `internal/terminalhistory` 的实际测试为准。

### 1.7 批量终端操作记录

用户授权的批量操作痕迹保存在 Panel 数据目录 terminal-batches/jobs.json（schema version 1）。
使用有界 JSON：任务数量不截断、每任务 64 台主机、文件最多 2 MiB、结束后保留 24 小时；活动任务和未确认释放的记录不按过期清理；目录 0700、文件 0600，
临时文件 fsync 后原子替换。只在任务准入、状态转换和删除时写入，不随输出轮询改写；同一 Manager 串行持锁写入，
当前为小型有界状态快照，无跨记录事务或复杂查询需求，暂不引入 SQLite。

持久内容仅含命令名/固定 k 动作摘要（不保存任意参数）、目标身份、创建/更新时间、逐主机状态和固定错误码。空格前缀命令只保留排除提示。
可执行命令与 PTY 输出只在内存；仅最近 10 轮每台最多 16 KiB 输出，总计最多约 10 MiB；成功准入后释放更早任务的输出，但保留完整记录。
界面自动恢复最近一轮，不新增记录选择和删除控件；未确认释放的会话沿用终止按钮重试。
操作记录不写入审计正文、标准日志或面板备份。重启将活动任务标为中断，输出不可用，绝不自动重放。
损坏/未知格式保留原件并停用新批量执行；首次准入落盘失败不发送命令，运行中落盘失败显式提示恢复风险。
RC19 及更早的批量索引读取器拒绝超过 10 轮的文件；回滚前须备份数据并恢复对应版本的数据备份，不可直接回退后继续写入新索引。已完成的真实主机操作不撤销；无需格式迁移或长期双写。
权限及故障注入有本地自动测试；Linux 文件权限、实际磁盘故障、跨节点与原生系统生命周期仍需隔离验收。

## 2. 分层选型

集群中心的远程访问选择保存到 Panel 数据目录 `cluster-remote-access.json`：单条 schema-v1 JSON，
最大 1 MiB，最多 4096 条主机独立偏好，目录 0700、文件 0600，首次显式修改才写入，沿用集群原子替换和 fsync，版本冲突拒绝旧表单。
总开关与主机偏好共用修订号，未单独配置的主机默认允许；总开关关闭不覆盖主机偏好，重新开启仍应用原有独立限制。
不增加后台写入、数据库或新常驻服务；配置保留至管理员修改。文件缺失且无替换残留时兼容默认开启；
损坏、未知格式、权限不符或存在未完成替换时保留原件并停止远程操作，监控继续可用，不以默认值覆盖。
配置纳入面板备份，恢复前由所属服务严格校验；旧备份没有该文件时保留目标中心已有选择。
回滚旧程序会忽略此文件，因而不再强制这些总开关；不删除或迁移配对与授权。需要继续禁用时不可依赖旧程序。

| 存储 | 适用业务 | 不适用业务 |
| --- | --- | --- |
| JSON | 小型配置、单对象快照、完成凭据、导入导出；写入频率低且可整体原子替换 | 持续增长的审计、频繁并发写、多条件查询、跨记录事务 |
| JSONL | 有界、追加写的监控采样和事件流；按日期分片并按保留期删除 | 高频随机更新、唯一约束、复杂关联和强一致事务 |
| SQLite | 单机 Panel 的账户、Session、审计、任务索引、通知、计划和结构化历史；需要事务、索引或分页 | Docker/Nginx/系统实际状态，多 Panel 共享写入，网络文件系统上的数据库 |
| PostgreSQL | 多 Panel 共享写入、主动高可用、多租户控制面或集中式大规模查询 | 当前单机轻量面板的默认安装 |

同一业务只能有一个权威写入存储。缓存必须可丢弃并可从权威数据或真实产物重建。

通用文件传输的任务索引位于 Panel 数据目录 `file-transfers/jobs-v3.json`，沿用有界任务 Store（100 项、
256 KiB、保留 7 天）。v3 增加同名策略、修订号及有界待决摘要（v2 的 BT 来源与来源校验进度保持兼容），JSON 外层仍为 `schemaVersion: 1`。
首次使用依次校验并复制 `file-transfers/jobs-v2.json`、`file-transfers/jobs-v1.json`、rc.13 的 `file-transfers/jobs.json`，
否则校验并复制旧 `remote-downloads/jobs.json`；原件保留供回滚，不进行双写。
历史跨主机批量任务也使用 `file-transfers/jobs.json`，但采用 `version: 1` / `items` 格式；仅识别其有界
JSON 外层并保留原件，不将它误读为通用任务或自动重放。未知、损坏或不可读的索引仍使后台任务不可用，
不以空历史替换；已存在的版本化通用索引是唯一权威来源。重启将活动任务标记为中断，
索引不保存完整下载 URL。跨主机记录只保存来源节点和目标主机标识。

BT 来源暂存位于 Panel 数据目录 `file-transfers/bt-cache`（目录 `0700`、正文 `0600`），不使用容器
`/tmp`，不属于面板配置备份。最多一个活动 BT 来源，只有一个最多 10 GiB 的平铺正文，文件名由程序
生成；种子路径从不用于打开缓存文件。完成、取消、失败时关闭引擎并删除正文；重启只回收能识别的
单个普通缓存文件，发现链接、未知条目或多余正文则停用 BT，保留异常现场。没有暂停缓存和自动续跑。
只在内存保留种子、磁力与 tracker 信息，不持久化链接或 passkey。校验完成后由公共 Agent receive
发布普通文件或受限 TAR 目录；单文件暂存峰值约两份、目录约三份数据，磁盘不足时任务失败且不发布
半成品。已发布文件不依赖该缓存，回滚旧程序仍可正常使用。

Agent 接收检查点位于自身文件回收站私有目录 `receive-sessions-v2.json`（512 KiB、32 个活动会话、
256 个含完成确认的记录、24 小时、创建时清理），临时正文位于目标的隐藏兄弟文件中，便于同一文件
系统内原子发布。正文与检查点同步后才确认分块；重启时验证已确认前缀并截断未确认尾部。
检查点损坏则拒绝恢复，不能把未知的半成品发布；完成确认通过原子发布前记录的资源身份查回。
同名候选首次读取旧 `receive-sessions.json` 后写入独立 v2 文件，保留旧索引供旧程序回滚。目录接收可关联
Agent 文件任务；完成、跳过与部分完成从关联任务的已确认结果读取，不重新执行已合并的目录。
文件任务索引为 Agent 私有 `archive-jobs-v2.json`，首次读取旧 `archive-jobs.json` 后保留原件，
继续使用 50 项、4 个活动任务、2 MiB、终态最多 7 天的边界；等待决定也计入活动名额。
这些私有运行文件不是用户文件或 Panel 配置的备份替代品。回滚到旧程序不读取新检查点，已确认完成
的普通文件/目录保持普通文件系统资源；未完成暂存由新版显式取消或到期清理。接收记录保留父目录、
正文暂存和私有发布目录的对象身份；仅清理仍能证明归属的对象，目录或暂存被替换时保留未知内容，
到期只移除失效检查点。Linux 发布从已打开的私有目录执行，普通文件通过持有的正文 inode 建立
临时硬链接后原子发布，不额外复制正文；目录在私有目录内解包后发布，仍需要归档与解包两份空间。

接收检查点会随每个已同步分块改写，连续传输可超过每秒一次。本次按下节条件评审过 SQLite：
该状态只为 24 小时内的暂存确认，容量限于 512 KiB、32 个活动会话和 256 条总记录，不承担长期
历史查询或跨资源事务；SQLite 也不能省略正文 fsync。当前保留有界私有 JSON，避免同时引入运行
存储迁移。旧/新传输基准显示新增校验和同步会影响吞吐及 CPU，但尚未独立归因 JSON 改写的 P95
和占比；扩大并发或检查点容量前须补该项测量，不能直接放宽限额。

## 3. SQLite 启用条件

以下任一条件持续出现时，必须进入 SQLite 方案评审，而不是继续扩大 JSON 文件：

- 单个可变 JSON 文件超过 `8 MiB` 或有效记录超过 `5,000`；
- 整体改写的写入 P95 超过 `50 ms`，或持续写入超过每秒 1 次；
- 产品需要跨记录原子事务、唯一约束、外键、稳定分页、组合过滤、聚合或全文检索；
- 多管理员并发、API Token、通知、计划任务或长期审计使数据关系明显结构化；
- JSON 解析、复制或整体落盘导致最近稳定基线的延迟、CPU 或峰值 RSS 回退超过 `20%`。

触发评审不等于立即迁移。实现前必须用真实规模数据比较 JSON/JSONL 与候选 SQLite 驱动的
二进制体积、空闲/峰值 RSS、读写 P95、磁盘放大、升级和恢复时间。

未触发以上条件且结构简单、有明确上限的业务可以长期保留 JSON；不得为了“技术统一”强制迁移。

## 4. SQLite 强制基线

SQLite 只能用于 Panel 本机持久化，并满足以下要求：

- 数据库位于本地文件系统；禁止放在 NFS、SMB 或其他网络文件系统。
- 数据目录权限为 `0700`，数据库、`-wal`、`-shm`、备份和导出默认 `0600`。
- 仅 `paneld` 持有数据库写权限；Agent 不读取 Panel 数据库，Panel 不因此获得宿主机目录权限。
- 使用参数化 SQL、固定 Schema 和白名单迁移；禁止任意 SQL、动态 `ATTACH`、运行时扩展加载。
- 默认启用 `foreign_keys=ON`、`journal_mode=WAL`、`synchronous=FULL`、
  `trusted_schema=OFF`、`busy_timeout=5000` 和 `mmap_size=0`。
- 连接数、事务时长、WAL 大小、查询返回量、分页大小和保留期必须有界；禁止无界全表加载。
- 数据库文件不是加密保险箱。密码继续使用 Argon2，Token 仅保存不可逆摘要；密钥和高价值凭据
  继续使用独立最小权限文件或专用 Secret。
- SQLite 驱动必须固定版本并纳入 SBOM、漏洞扫描和许可证审查。选型须比较 CGO、跨架构构建、
  scratch 镜像兼容、二进制体积和运行时内存，验证前不预先指定驱动。

备份必须使用 SQLite Backup API 或 `VACUUM INTO` 等一致性方式；WAL 模式下不得仅复制主
数据库文件。恢复前校验格式、摘要、Schema 版本和可用磁盘空间。

## 5. 数据模型规则

- Schema 和迁移版本必须单调递增，迁移过程可重复检测，不得依赖页面是否打开。
- 高频历史数据按时间范围查询并设置保留期；大日志、归档和二进制文件不直接写入数据库。
- 审计保存动作、对象、结果和必要上下文，不保存明文密码、Token、Cookie 或完整环境变量。
- 面板缓存字段必须带采集时间和来源；缓存失效时显示未知或重新读取，不能伪装成真实状态。
- Repository/Store 接口应隔离业务逻辑与存储实现，禁止在 HTTP Handler 中散落 SQL 或文件写入。

## 6. 迁移与回滚

JSON → SQLite 的迁移必须按以下顺序实施：

1. 先建立存储接口、Schema、限额和兼容测试，不同时改动无关业务。
2. 在真实规模副本上验证性能、资源占用、损坏输入、并发写和低磁盘场景。
3. 升级前生成可恢复的 JSON 备份；迁移在单个 SQLite 事务中完成。
4. 校验记录数、关键字段、唯一约束、摘要和 `integrity_check` 后，原子切换存储标记。
5. 不进行长期双写。短期灰度双读只能用于比对，必须有截止版本和删除计划。
6. 回滚通过版本化 SQLite → JSON 导出或恢复升级前备份完成；不得直接让旧二进制读取新 Schema。

自动迁移、默认启用或删除旧数据属于 L3 发布；必须覆盖升级中断、重启恢复、回滚和跨架构实机
验收。实验性存储只能显式启用，不能让新旧用户获得不同且无法解释的数据语义。

## 7. 测试与验收

新增或修改持久化业务至少验证：

- 空库、新建、读取、更新、删除、分页、过滤和并发写；
- 旧版本升级、重复启动、迁移中断、磁盘写满、只读文件系统和损坏文件；
- 原子性、唯一约束、外键、权限、敏感字段脱敏和超限拒绝；
- 备份、恢复、回滚、`integrity_check` 和旧格式兼容；
- 真实规模下的二进制体积、空闲/峰值 RSS、读写 P95、磁盘增长与基线对比；
- `amd64`、`arm64` 和正式支持的 Linux 发行版。

每次设计评审必须明确：权威事实来源、选用的存储、容量模型、保留期、事务边界、查询模式、
安全边界、迁移版本、备份恢复和回滚点。

## 8. PostgreSQL 边界

只有出现多 Panel 共享写入、主动高可用、多租户隔离或单机 SQLite 已有实测瓶颈时，才评估
PostgreSQL。引入前必须给出连接管理、部署依赖、备份恢复、网络加密、凭据轮换、离线降级和
运维成本方案。当前单机产品不得仅为“以后可能集群化”提前增加外部数据库依赖。

## 9. 音乐文件头缓存实现

`DataDir/music-metadata-v1` 保存可丢弃的文件头解析结果：歌名、歌手、专辑和编码质量，来源固定为
`file-header`，带解析时间与 Schema 版本。键包含主机、绝对路径、文件资源版本和字节数；文件变化即
失效。音频原件仍是权威事实，不改标签，不把图片 Blob 或歌词复制进此缓存。

每条独立 JSON 原子写入，最多 4096 条、总计 16 MiB、单条 12 KiB，保留 180 天；启动与写入时清理
过期条目，容量不足按最早写入淘汰。目录权限 0700、文件 0600；不跟随符号链接，读取与批量请求均有界。
不完整、损坏或过期记录作为未命中重新读取；缓存不可用时回退到音频文件，不影响播放。

此缓存不要求备份；恢复或回滚可直接舍弃该专用目录后重新生成，不迁移成音乐资料库。在线歌词和封面
继续采用歌曲同目录侧车文件，已有本地内容优先且不覆盖。浏览器内存仅保留最多 256 条观察结果，退出
账户清空；只为可见歌曲按需解析，两个并发、每次六秒预算，初始列表最多批量查询 64 条缓存。
