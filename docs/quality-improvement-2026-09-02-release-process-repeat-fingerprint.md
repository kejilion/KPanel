## 观察证据

- 可重复观察：`v0.98.1` 的 `kpanel-release-process-incidents` 区块声明两个指纹，两者都已在
  `v0.98.0` 出现，但两条明细的 `historicalReleases` 均为 `[]`。滚动 5 个版本内同指纹出现 2 次，
  按 5.1.7 已构成“重复流程缺陷”，而当时既无机器提示，也无验收记录侧的重复声明。
- 精确环境、版本、时间范围和样本量：`origin/main@89a384c`，`docs/` 下 162 份验收记录，
  覆盖 `v0.71` 至 `v0.100.0`；重点样本为 `v0.98.0`/`v0.98.1` 相邻两版。
- 原始命令、日志、截图或验收记录：

  ```bash
  node scripts/report-release-metrics.mjs --days 14 --releases 20 --format markdown
  node scripts/report-release-metrics.mjs --validate-acceptance docs/release-v0.98.1-acceptance.md
  ```

  改动前第二条命令通过，不报告任何重复；改动后仍通过（低于生效版本下限），但滚动报告新增
  “重复流程异常指纹”小节，把该重复显式列出。
- 已确认事实：5.1.7 原文把重复判定交给人工（“机器只校验计数和必需结构；流程复核者必须读取原始
  日志并比较最近 5 个验收记录”）。`scripts/report-release-metrics.mjs` 改动前只校验单份记录内部的
  计数与结构一致性，跨版本比较没有任何机器入口。
- 未确认信息与数据缺口：无法确认 `v0.98.1` 的复核者是否人工发现了该重复而选择不声明；验收记录
  不可变，不追溯改写，因此该问题只能从下一个版本起防止。缺失的验收记录（如 `v0.82.0`）不能推断为
  “无重复”。
- 为什么不是一次偶发环境故障：这是规范条款缺少机器入口导致的系统性盲区，与运行环境无关；同一条款
  的计数与结构部分已有机器校验并稳定生效，只有跨版本比较部分依赖人工。

## 原因假设

- 待验证根因：5.1.7 的重复判定只有人工执行路径。在 14 天 40 个正式版本的发布节奏下，人工逐版比较
  最近 5 份记录不具备可持续性，重复指纹因此可以在结构校验全绿的情况下静默通过。
- 可能的替代解释：（a）复核者已发现但认为属上游瞬时故障——但 5.1.7 要求此种情况建立有期限例外并
  保留原始证据，`v0.98.1` 无此记录；（b）指纹被改名导致漏配——已排除，两版指纹字符串完全一致。
- 能证伪本假设的结果：若历史上存在验收记录在 `historicalReleases` 中主动声明重复的先例，说明人工
  路径可用，问题只是个案。已检索全部 162 份记录，未发现非空 `historicalReleases` 的先例。
- 是否涉及 `kejilion.sh`、真实系统资源、Panel/Agent 权限边界或兼容契约：否。改动只涉及仓库治理脚本
  与其单元测试，不触碰产品代码、运行时和权限边界。

## 产品原则与核心思想对齐

- 对业务真源和双端互通的影响：无。验收记录仍是唯一发布证据真源，指标入口仍是
  `scripts/report-release-metrics.mjs`，不新增第二真源。
- 对轻量、低资源、单管理员控制面的影响：无运行时影响。新增比较只在验收校验和滚动报告时读取同目录
  最多 5 份 Markdown。
- 对安全、稳定、性能、体验、数据/迁移的影响：仅提高发布流程稳定性；不改变 fail-closed 语义方向
  （只增加阻断条件，不移除）。
- 不应引入的复杂度或第二真源：不建平行校验脚本、不引入指纹数据库或缓存、不改变验收模板结构。

| A：在唯一入口 `report-release-metrics.mjs` 内补跨版本比较，设版本生效下限 | 复用既有校验路径与门禁路由；历史记录零回归；报告与阻断同源 | 需要读取同目录兄弟文件，引入文件系统依赖 | **采用**。不新增入口，与既有两个版本下限写法同构，符合“唯一仓库脚本”要求 |
