# KPanel 多智能体会话协作

## 使用方式

用户只需在 `KPanel · 协调中心` 描述目标。协调中心先通过 SSH fetch 盘点远端任务分支、worktree
和活跃任务，形成标准任务契约并确认 Definition of Ready，再按能力和冲突面选择 Codex、Claude 或
其他智能体；结果返回后按 Definition of Done 和标准交付包统一验收。

完整的角色、跨智能体真源、worktree 隔离、状态流转、发布冻结、交接、冲突恢复和权限规则以
[`project-management.md`](project-management.md) 为准；具体运行方式见
[`multi-agent-collaboration.md`](multi-agent-collaboration.md)。本文件只保留日常使用入口。

建议用一句话同时说明目标和验收标准，例如：

```text
检查应用市场安装终端卡住的问题，修复后跑相关 Go 测试，不要部署。
```

## 会话分工

| 标题 | 职责 |
| --- | --- |
| `KPanel · 协调中心` | 接收需求、路由、跟踪、验收、汇总 |
| `KPanel · <AI> · 分析 · <领域>` | 只读排查、设计和风险分析 |
| `KPanel · <AI> · 开发 · <领域>` | 在明确文件范围内实现修改 |
| `KPanel · <AI> · 验证 · <领域>` | 独立运行测试和复核结果 |

会话 ID 不写入项目。SSH 远端分支、聚焦提交、CI 和发布记录构成跨工具索引；标题、项目路径和
会话状态只用于各 AI 工具内部恢复。GitHub Issue、PR、API 和 `gh` 登录不作为协作前置条件。

## 并发与工作树

- 管理工作树只用于 fetch、盘点和只读比较；项目在工具 UI 中如何注册不改变这一规则。
- 共享目录中的只读分析可以并发；每个写任务必须独占一个专用 worktree 和分支。
- 同一业务域、共享 API/Schema、锁文件、版本文件或候选文件有重叠时先串行或明确依赖。
- 尚未交付的会话可以复用，但恢复前必须重新核对远端提交、工作树、负责人和权限，不能依赖旧会话记忆。
- 候选已交付时执行 [`project-management.md` 10.1](project-management.md#101-发布接管后的责任)：由发布任务独立闭环，不召回原任务。

## 决策顺序

1. 读取共享项目规则，执行 `git fetch origin --prune` 并核对当前 Git 状态。
2. 查找同领域、同路径范围的远端分支、worktree 和跨智能体任务。
3. 对尚未交付的开发工作，无冲突且任务契约仍一致时继续旧任务；否则创建专用 worktree、任务分支和目标智能体任务。不得用此规则返派已进入发布通道的候选。
4. 执行者完成聚焦差异和对应等级验证；获授权后形成提交并通过 SSH 推送任务分支。
5. 协调中心从精确差异/提交独立复核，补齐未覆盖证据，再向用户统一说明修改、验证、风险、权限状态
   和知识沉淀。
6. 发布接管后，协调中心等待完成交付，不定时催问或逐项审批；发布任务自行完成剩余验证和修复，交付结束后再安排下一轮。

可复用的完整执行步骤见：

- `.codex-workflows/session-collaboration.workflow.yaml`
- `.codex-workflows/release-kpanel.workflow.yaml`

历史工具链测试不是当前协作成功依据。跨工具状态始终以 SSH 远端提交、CI、Release 和验收记录为准。
