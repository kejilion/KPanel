# KPanel 质量改进提案：协作隔离与发布流程降噪

- 提案状态：待复核
- 提案日期：2026-08-20
- 负责人：KPanel 协调中心
- 适用业务域：多智能体协作、发布执行与治理门禁
- 基线提交 / 标签：`91583a311da9e31346c5e9ca4f628c35ce98494e` / `v0.88.1`
- 关联缺陷、验收记录、CI 或事件：`release-v0.83.0`、`v0.85.0`、`v0.86.2`、`v0.88.0`、`v0.88.1` 验收记录；主线 CI `32349386636`
- 提交、推送、发布和生产权限：允许在专用规范 worktree 修改；未授权提交、推送、更新 `main`、发布或操作生产

## 观察证据

- 可重复观察：规范已明确要求独立 worktree 和发布单写者，但管理工作树仍出现业务文件未提交、
  本地 `main` 存在未进入远端的提交；发布验收已能 fail-closed，却连续记录 Runner、跨 Shell 命令、
  环境依赖、测试预算和证据断言类重复流程异常。
- 精确环境、版本、时间范围和样本量：2026-08-20 在 Windows 管理工作树及
  `origin/main@91583a3` 的独立干净 worktree 复核；发布指标窗口为 7 天及最近 20 个稳定版本。
- 原始命令、日志、截图或验收记录：
  - `git status --short --branch`：管理工作树 `main` 当时领先 `origin/main` 7、落后 74，并有 10 个业务文件未提交；
  - `node scripts/report-release-metrics.mjs --repo . --ref HEAD --days 7 --releases 20 --format json`：
    29 个稳定标签、21 个生产完成记录、验收覆盖 19/20、生产完成证据 18/20、提交到生产中位数 0.89 小时；
    有流程指标的 11 个版本共记录 51 次流程异常，其中生产写操作开始后 13 次；
  - `docs/release-v0.88.0-acceptance.md` 和 `docs/release-v0.88.1-acceptance.md` 分别记录 10 次和 11 次
    流程异常，均未造成产品失败、数据损坏、回滚或门禁逃逸；
  - `node --test` 治理回归 44/44、10 个工作流结构验证、主线 CI 均通过。
- 已确认事实：质量门禁能够阻断错误成功；当前问题是执行入口和环境准备不够稳定，以及已有工作树
  隔离规则缺少可复用机器检查，不是性能、安全或稳定门槛不足。
- 未确认信息与数据缺口：历史流程异常没有稳定指纹，不能可靠计算每个根因的精确复发次数；下一观察
  窗口必须从新验收记录建立指纹基线。
- 为什么不是一次偶发环境故障：跨 Shell 转义、Runner/运行时依赖、证据断言和备份复核类问题跨多个
  版本重复出现；管理工作树偏离规则也可由标准 Git 状态直接复现。

## 原因假设

- 待验证根因：硬规则停留在文档层；发布异常只统计总数，没有以“阶段/权威入口/根因类别”形成稳定
  指纹和复发处置；生产写前仍允许临时拼接跨 Shell 命令和首次发现运行时依赖。
- 可能的替代解释：高频发布和复杂 L3 本身会增加原始异常数；部分网络或上游故障不可由本地预检消除。
- 能证伪本假设的结果：引入检查和复发规则后，管理工作树违规仍无法被检测，或相同可预防指纹继续
  复发且发布用时、误阻断或产品变更失败率明显恶化。
- 是否涉及 `kejilion.sh`、真实系统资源、Panel/Agent 权限边界或兼容契约：不改变上述契约；只约束
  协作和发布控制面。

## 产品原则与核心思想对齐

- 对业务真源和双端互通的影响：无业务行为变化，不建立第二真源。
- 对轻量、低资源、单管理员控制面的影响：新增检查只在任务启动、候选冻结和治理验证时短时运行，
  不增加 KPanel 常驻进程。
- 对安全、稳定、性能、体验、数据/迁移的影响：不降低任何门禁；通过减少生产写后临时修正提高稳定性，
  对产品运行时性能、界面和数据格式无影响。
- 不应引入的复杂度或第二真源：不建设会话台账或常驻协调服务；Git、CI、验收记录继续是真源。

## 最小改动方案

- 预计修改文件或唯一入口：新增 `scripts/check-collaboration-state.mjs` 及测试；其余规范和工作流只引用
  该入口，并在现有发布验收模板补异常明细要求。
- 新增或调整的自动门禁：管理角色必须是主工作树、`main`、clean 且不领先基线；写角色必须使用链接
  task worktree、非 `main`，在启动/验收 checkpoint 可要求 clean；外部 `GIT_*` 不能改变证据来源。
- 迁移、兼容和失败恢复：管理树落后远端只报告不失败，避免强迫本地 `main` 写入；检测失败只隔离该
  管理树，协调中心仍可从精确 `origin/main` 创建专用 worktree，不清理或覆盖未知改动。
- 防止指标投机或规则自我弱化的约束：不以减少异常计数为目标；不得漏记、合并不同事件、删除测试、
  放宽 fail-closed 或把生产失败改名为流程异常。
