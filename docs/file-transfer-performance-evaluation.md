# 文件传输加速可行性实测

日期：2026-10-09 至 2026-10-10。分支：`feature/file-transfer-acceleration`。本记录属于本地候选评估，不是发布验收。

本页保留两个阶段：先测固定并发原型，再测智能 HTTP 与原生 BT 的产品候选。
当前候选的实现与结果见文末“第二阶段：智能 HTTP 与 BT 候选”；以下直到该节的“本轮”均指第一阶段，
其中“默认关闭、没有界面开关”的描述不代表后续智能候选。

## 第一阶段：固定并发原型

结论：单文件多路 HTTP Range 在当前架构下可以实现，但本轮未证明适合默认启用。来源受限时有收益；
来源已经足够快、目标写入受限或每个请求有明显额外延迟时，收益会消失甚至回退。额外内存也不能忽略。
第一阶段结束时保留可重放原型，普通 `NewServer` 不启用预取，默认 URL 客户端仍使用 `Open`；
没有新增产品设置或用户界面开关。基准通过显式测试入口启用实验能力。

## 架构与实现边界

现有路径是 `公开 URL → 非 root Panel → Agent 接收会话 → 暂存文件 → 原子发布`。
Panel 原先逐个读取 8 MiB，发送给 Agent，等待正文与检查点持久化确认，再读下一块。
已有来源重连、强 ETag 条件 Range、前缀摘要和幂等确认；已有能力不是单文件多路下载。
后台最多两个传输任务，Agent 仍按顺序确认偏移。本研究没有改动该协议、文件权限或 `fsync`。

| 原型 | 实现 | 本轮取舍 |
| --- | --- | --- |
| 单流预取 | 已知长度至少 16 MiB 时，在接收会话建立后增加 4 MiB 缓冲，重叠来源读取和目标写入 | 收益有限，默认关闭 |
| 多路分段 | 至少 32 MiB、不超过 10 GiB，长度已知且有强 ETag；2–4 个 worker 领取固定 2 MiB 片 | 正式对照使用 2 路，默认关闭 |
| 来源一致性 | 每片复核强 ETag、最终 URL、精确 Content-Range、长度、编码和实际正文结束 | 变化立即失败，不能通过重连掩盖 |
| 有界排序 | 在途片、已完成片、当前消费片共用固定的 worker 数量缓冲；不随文件大小增长 | 2 路至多 4 MiB，4 路至多 8 MiB，不叠加预取 |
| 兼容与恢复 | 探测前关闭首个 200 Body；源站忽略 Range 时使用探测返回的完整 200；网络截断从已持久确认偏移恢复 | 保留原次数上限和摘要校验 |

此处“动态”指窗口内按消费进度继续领取小片，不包含 IDM 式在途大段再次二分、测速调节连接数、
镜像竞速、跨进程持久分片或整机带宽调度。不能宣称已实现完整 IDM。
HTTP 允许源站忽略 Range，弱 ETag 不能用于 If-Range；本实现按
[RFC 9110 Range](https://www.rfc-editor.org/rfc/rfc9110.html#section-14.2) 与
[If-Range](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.5) 检查响应，而不只相信 `Accept-Ranges`。

## 不同文件操作能否受益

| 操作 | 可复用范围 | 结论 |
| --- | --- | --- |
| URL 下载到服务器 | 预取和多路 Range | 有条件适用，最值得继续研究的场景 |
| 跨主机普通文件 | 可复用有界预取；多路读取需另做已鉴权来源适配 | 本轮未测 HTTPS/Noise 跨主机收益 |
| 浏览器上传 | 共用 Agent 接收会话，但不经过该 Panel 读取循环 | 本轮没有加速；单文件并行上传需要接收端乱序/确认协议改造 |
| 目录传输 | 当前是未知长度受限 TAR 流，不满足这里的长度与 Range 条件 | 不启用 |
| 同机复制/移动 | 本地文件系统操作 | 不适用该 HTTP 分段方案 |
| 下载到用户电脑 | 浏览器/download ticket 链路 | 本轮没有改变；需要客户端配合 |

## 实验身份与测量方法

- 基线：`e4f7e19bf8e1440d262e23355263e844e9a3dd63`。相关 Panel 接收器、来源适配器、
  `internal/filemanager`、Agent 接收入口、`internal/remotedownload`、`internal/httpstream` 与稳定版
  `v1.25.0` 无差异；此比较仍是冻结源码夹具，不冒充完整稳定版部署比较。
- 正式性能原型：`ee243e8545ac98aeaa1b26957bc91bd6b1c3d78d`。该实验提交开启预取以测量，
  后续默认关闭决定与测试入口调整不倒写为该 SHA 的行为。
- 环境：已通过用途检查的 `arena-154`，Linux amd64、8 个可见 CPU、约 8 GiB 主机内存，真实磁盘。
  测试没有连接生产 Agent，没有修改主机网络整形，也没有发布或部署。
- 工具镜像：Go 1.27.2 / Node 24.21.0，固定 ID
  `sha256:20667a9f1fad6590219ba8d8acdabc09a49f8683d4a877b847df17d28b83f8fb`。
- 编译在独立 2 CPU / 2 GiB 工具容器；每个测量进程使用 1 CPU、256 MiB 内存且禁用额外 swap、
  128 PIDs、16 MiB tmpfs，`GOMAXPROCS=1`、`GOMEMLIMIT=192MiB`。这两个 Go 参数属于相同的夹具配置，
  不是生产调参建议。正文与临时目录位于任务专属真实磁盘目录，非 tmpfs。
- 原站是实际 HTTP/1.1 服务；通过测试 Resolver/Dialer 将公开测试域名映射至回环，保留产品 URL
  校验代码。接收端使用真实 Agent 文件路由与 filemanager，实际校验、同步、持久确认和提交。
- 每场景、每方案独立预热一次，然后交错轮换运行 5 次；共用主机和热页缓存，报告中位数及最小/最大值。
  每个样本启动新测试进程，预热不消除连接建立成本，也不是运行中 Panel 的进程预热。
  样本不足以报告 P95。任何差异落入波动范围都不能宣称改善。
- 计时覆盖 `executeFileRemoteDownload` 至 Agent 提交完成，包括来源探测、目录查询、创建会话、
  分块确认和最终提交；不包括准备测试数据和测后校验，也不包括浏览器、登录、后台排队、任务索引终态持久化。
- 每次校验完整文件 SHA-256 与大小，输入每 64 KiB 写入绝对块偏移，能够识别 2 MiB/8 MiB 整片重复
  或换位。另记录来源请求数、来源实际成功写出字节、Agent 请求正文总量和原站最大活跃处理程序数。
- CPU/RSS 来自原站、Panel、Agent 合并的测试进程，RSS 为本进程高水位；不是独立 Panel RSS。
  限速为每个 HTTP 响应 8 MiB/s，请求延迟为处理程序延迟 20/100 ms，都不是测得的公网 RTT。

可支持的结论：

- 来源限速场景，2 路从 8.065 s 降至 6.172 s，耗时减少约 23.5%，吞吐约 1.31 倍；波动范围分离。
- 同条件两个任务从 8.126 s 降至 6.574 s，耗时减少约 19.1%；同源最大活跃请求观察到 4 路。
- 来源和目标均限速时，2 路从 10.465 s 增至 12.495 s，耗时增加约 19.4%。256 MiB 快速源中位耗时也增加约 21.0%。

- 2 路在多个单文件场景的最大 RSS 比基线高约 26%–28%；预取在 100 ms 请求延迟场景也高约 22%。

- 64 MiB 的 2 路分段需要 33 次来源请求（1 次初始 GET + 32 个片）；基线为 1 次。
  256 MiB 为 129 次，双任务共 66 次；忽略 Range 时为 2 次并回到完整单流。小文件每件均为 1 次。
- 快速源的初始 GET 被关闭前仍可能写出额外正文；64 MiB 部分样本共约 67.7 MiB 来源正文。
  限速源正式样本正文总量仍为 64 MiB。此计数是 HTTP handler 成功写出的正文，不含 TCP/TLS 开销。

## 可靠性与评审

定向测试覆盖真实 EOF 与传输错误区分、预取背压/关闭、分段短读/超长/错误结束、强验证器/范围/
编码错误、Range 忽略回退、慢首片窗口上限与取消回收；真实 HTTP 到 Agent 的大文件用例覆盖
来源截断后从已确认的 8 MiB 恢复、分块/提交确认丢失、大文件取消及暂存清理。
分段一致性错误用例断言不得 suffix 重连或发布目标。

独立复核曾发现“来源一致性错误被普通重连掩盖”和“周期性夹具无法识别整片错位”，均已修复；
编码故障夹具进一步使用准确长度并断言错误码，避免被其他检查遮蔽。
早期 `smoke-r1`、`formal-r1` 保留原始记录，但不进入正式结果。`formal-r1` 因夹具修正主动中止，
中止容器状态不是产品 OOM 或下载失败。

## 性价比与下一步准入

当前更适合保留为研究分支，暂不把加速接入默认产品行为。来源受限时可以节省时间，
但多出大量 Range 请求，内存增加，还可能把瓶颈推向目标写入；增加 worker 并不等于等比例提速。
单流预取复杂度较低，但本轮不足以证明其默认收益，不能只凭理论流水线收益启用。

若继续产品化，优先研究“慢且支持 Range 的大文件才启用、快速源保持单流”的自适应策略，
并降低瞬时内存、保留统一的持久确认语义。先过独立 Panel/Agent 的 256 MiB 资源与控制面响应预算，
再测真实 WAN、HTTP/2、HTTPS/Noise、弱网中断和双任务公平性。不要通过删 `fsync`、放宽来源校验或
增大产品内存预算换取数字。

本轮没有验证 10 GiB 实际传输、断电、重启后自动续传、磁盘满、真实公网服务的限流策略，
也没有执行 CF scoped/full 安全审计。CF 审计明确 deferred：功能仍在隔离试验分支，稳定集成前按
项目规则以指定的 `gpt-6-luna` / `max` 审计补齐；本记录不是安全审计通过证明。

## 第二阶段：智能 HTTP 与 BT 候选

本阶段已加入产品入口：原远程下载对话框支持 HTTP/HTTPS、v1 .torrent 文件/地址和公开 btih 磁力，默认开启智能加速，可手动关闭。当前 HTTP 从 1 路试探 2 路；BT 从 4 个已建立连接试探 8/16 个。它们根据有效传输速度与写入/内存压力决定是否保留扩容，不按 CPU 核心数等比例设并发，也不承诺固定 20% 收益。

BT 是统一传输层的来源适配器：协议分片先在 Panel 私有目录暂存和校验，随后交给原 Agent receive；目录转换为有界 TAR。原任务队列、8 MiB durable ACK、来源/目标摘要、幂等重试与原子发布共用。BT 同时最多 1 个，所有传输仍共用 2 个任务槽；HTTP 并行额外读缓冲全局最多 8 MiB。HTTP 固定 4 路仅在本页实验入口启用，未改成产品默认。

能力边界：不支持 v2/hybrid、私有磁力、做种或完整 BT 客户端管理。私有下载必须事先导入 .torrent，以便在发现节点前关闭 DHT/PEX；公开磁力可能在获知元数据前使用 DHT，不提供私有磁力的隐私保证。单任务仍受 10 GiB 限制；BT 要额外的 Panel 暂存磁盘，发布时目标还需要空间。重启把未完成任务标为中断，不能跨重启自动续传。

### 冻结版本与测量边界

- HTTP 智能开关、BT、固定 2/4 路使用同一个 `ef8576ae6ec2128d8607475a1c2bc9b9cb3e4e89` 测试二进制。慢源补测使用 `3553f0c61e306e1fe1777a3e1c6c419f2718cb5d`，只增加 2 MiB/s 夹具及脚本 case 白名单；产品代码和依赖与 ef8576ae 相同。每个比较组均使用同一二进制，排除新 BT 库本身的固定成本。
- arena-154，沿用第一阶段固定 Go/Node 镜像；每进程 1 CPU、256 MiB memory/memory+swap、128 PIDs、network none，实际文件系统，GOMAXPROCS=1、GOMEMLIMIT=192MiB。构建、race 和浏览器重负荷没有与正式性能轮同时执行；主机不是独占机器，磁盘时延仍有波动。
- 每组独立预热，随后交错运行 3 次。HTTP 覆盖 9 个开关场景及 4 个固定并发场景，额外 1 个慢源场景；BT 比较 8 个限速种子节点和仅 1 个节点。BT 夹具使用 64 MiB 自建数据、256 KiB piece；多节点每节点 512 KiB/s，稀缺节点 2 MiB/s。
- 耗时直到真实 Agent 提交完成，包括 BT 暂存/分片校验和最终发布。CPU/RSS 是合并原站或种子、Panel、Agent 的测试进程；RSS 是进程高水位，包含夹具准备，不是独立 Panel 峰值或生产资源准入证明。未测独立控制面响应或实际公网 RTT。

102 次测量和 34 次预热全部通过完整 SHA-256/大小校验；136 个容器均退出 0、OOMKilled=false。没有收集 memory.events，因此不把此结果解释为没有触碰过 cgroup 限额。以下时间为秒，均为中位数 [最小–最大]，每格 n=3；资源为 CPU 秒中位数 / 最大 RSS MiB。

### 取舍、验证与复现

“提速 20%、内存增加 20%”不是最佳点或产品目标。并发收益取决于原站是否按连接限速、共享带宽、磁盘确认开销、可用 peer 和任务数量；核心数只能为资源预算提供参考。当前保留 HTTP 最多 2 路的保守自动策略及全局缓冲预算，固定 4 路实验用于评估潜力，不据有限场景直接放宽默认上限。BT 已按收益尝试扩容，有压力或无收益就收缩。

开发验证覆盖真实 HTTP/BT 到 Agent 的文件与目录、完整哈希、取消清理、源变化、错误 Range、暂时探测失败、丢失分块/提交 ACK、恶意元数据、网络地址限制和私有种子/磁力策略。正式测量前 ef8576ae 的三个相关包测试与依赖门禁通过；最后本地候选的 L2/race/浏览器收据单独绑定交付 SHA。界面证据是 mock，不代替真实协议测试。
