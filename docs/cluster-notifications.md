# KPanel 集群通知设计与实现边界

- 状态：Telegram、飞书、钉钉、企业微信四个通道已实现；真实平台联通、隔离真机和正式发布仍按本节验收边界执行
- 入口：`集群 → 通知`（设置）、`活动记录 → 通知记录`（历史）
- 目标：在不引入常驻队列、数据库或额外 Agent 权限的前提下，让一个 KPanel 统一通知本机和全部已接入主机

## 1. 设计取舍

通知是 KPanel 控制端的派生能力，不建立第二份主机资源事实：

- CPU、内存、磁盘、收发流量直接消费既有 `cluster.HostList` / `HostSnapshot`；
- 掉线沿用集群现有 `online`、`degraded`、`stale`、`offline`、`auth_failed`、`tls_error`、`incompatible` 状态机；
- SSH 登录只新增窄字段 `HostTelemetry.SSHLogin`，不传递原始认证日志、SSH 配置或凭据；
- 配置使用有界 JSON，活动通道凭据与状态分文件保存；不引入 Redis、SQLite 或消息队列；轻量节点的
  SSH 读取只增加受限 root broker，不下发 Bot 凭据，也不让遥测进程获得 root 权限。

Telegram 接入只要求用户输入 BotFather 生成的 API key。KPanel 通过 Telegram Bot API `getMe` 校验机器人，
再读取有限的 `getUpdates`，自动寻找用户私聊机器人后发送通知；用户不需要输入 `chat_id`。第一次接入时，
用户需要先私聊机器人发送 `/start`。如果机器人正在使用 webhook，界面会明确提示，不会静默覆盖 webhook。

飞书、钉钉和企业微信复用群机器人生成的完整 Webhook 地址，不需要 `chat_id`。KPanel
只接受各平台官方 HTTPS 主机和固定路径/查询参数，不提供任意 Webhook 或自定义请求功能。保存新
Webhook 前先发送一条本地化验证消息，只有返回各平台预期成功结构才落盘。

## 2. 交互

集群页 Hero 区只增加一个“通知”入口，打开一张轻量弹窗：

1. 四张通道卡片都显示未配置、已连接或需要检查；Telegram 额外支持“等待私聊”。任何卡片都不显示 token、Webhook 或 `chat_id`。
2. 同一时间只保存一个活动通道。凭据输入框留空表示保留当前通道原值；切换通道必须输入新凭据，保存后替换旧凭据。
3. Telegram 的“保存并连接”完成校验、私聊发现和落盘；机器人通道的“保存并验证”先真实发送测试消息再落盘。
4. “重新发现私聊”只在 Telegram 中出现；“发送测试消息”在四个通道就绪后都可用。
5. 外部推送开关保留全部阈值与事件开关；关闭只暂停外部发送，本地事件记录默认持续运行。规则可在未配置渠道时保存。
6. 资源规则使用启用复选框加阈值；累计接收和累计传送分别配置，事件规则只使用开关，不增加分散的高级配置。服务器到期提醒在此统一勾选，覆盖所有已填写有效日期的主机（含后续添加的主机）；主机管理不再显示逐台提醒开关。
7. 通知语言在保存设置时记录当前 KPanel 界面语言（简体中文、繁體中文或 English），之后不随其他浏览器或页面临时切换而漂移。
   面板在线提示跟随当前界面语言；事件正文沿用保存时的消息语言。
8. 消息时间使用通知中心这台 KPanel 宿主机的 Agent `management.timezone`，并始终附带明确的 `UTC±HH:MM` 偏移；
   读取失败时回退当前进程时区，存储时间仍统一使用 UTC。

所有集群主机（包含本机）复用同一组规则。界面说明连续 3 次采样才触发，恢复只发送一条恢复消息；未知、
无效或零值指标不产生资源告警。弹窗支持已有 `ModalDialog` 的 Escape、焦点回收、键盘 Tab、桌面/移动视口和
浅色/深色 semantic token。移动窄屏下“添加主机”单独占满操作区，避免被挤到下一行后变成无内容的矩形。

## 3. 告警语义

| 类别 | 条件 | 去重与恢复 |
| --- | --- | --- |
| CPU / 内存 / 磁盘 | 有效百分比达到阈值，默认 90% | 连续 3 次后告警；低于阈值发送恢复；持续告警最多每 6 小时重复 |
| 流量 | 收发总速率达到阈值，单位 MiB/s，默认关闭 | 首次使用集群已有速率，之后使用计数器差分；计数器回退或速率无效时跳过 |
| 累计接收 | 每台主机的累计接收字节达到独立阈值，默认关闭 | 与概览桌面监控小组件同源、同样使用 1024 进位和 1 位小数显示；达到后每个计数器周期只告警一次，计数器回退/重启归零后重新计数，不发送“恢复” |
| 累计传送 | 每台主机的累计传送字节达到独立阈值，默认关闭 | 与累计接收独立去重、独立重置和独立通知 |
| 掉线 / 失联 | 集群状态连续 3 次处于 stale、offline、auth_failed、tls_error 或 incompatible | 未达到连续次数便恢复时不发送告警或恢复；告警后恢复到 online/degraded 才发送恢复；单次评估最多外发 8 条，失败 5 分钟后重试，最长 24 小时 |
| 服务器到期 | 全局规则开启，主机有有效到期日期；不依赖在线状态 | 按中心端时区提前 7、3、1 天和当天各一次；日期与档位持久化去重，关闭后取消未发送重试，重开不重复已记录档位 |
| SSH 登录 | 出现新的、通过校验的 `SSHLoginEvent.ID` | 首次观测只建立基线；之后每台主机按事件 ID 去重，只发送用户、来源、方式、发生时间 |
| 面板登录 | 本 KPanel 的密码或通行密钥登录成功，规则默认关闭 | 每次登录一条，不去重、不发恢复；只发送用户、来源 IP、登录方式和时间，见[面板登录通知](#面板登录通知) |

累计接收和累计传送始终直接使用既有 `NetworkSummary.ReceivedBytes` / `SentBytes`，不再创建收发合计指标；
前端集群卡片、公开分享和概览桌面监控统一复用同一个方向格式化器，通知消息也按相同的 1024 进位和 1 位小数呈现。
这样调整收发任一方向的单位或精度时，只需要修改对应共享层并同步验证，不会出现各页面各算一套的情况。

通道发送统一使用 6 秒超时，后台评估默认 30 秒一次；所有网络调用均使用固定 HTTPS API 根地址、TLS 1.2、禁止重定向、
64 KiB 有界响应体和最大并发/发送数；机器人回应还必须符合对应平台的成功结构。发送失败只影响通知通道状态，不改变集群主机状态，
也不阻塞浏览器读取。

## 4. 存储与恢复

数据目录下新增 `notifications/`：

- `notification-state.json`：开关、规则、通道状态、资源版本和最多 1024 个有界告警状态；权限 `0600`；
- `notification-history.json`：本地事件、投递状态和告警评估游标原子保存；最多 2,000 条、4 MiB、30 天，先达到的限制生效；权限 `0600`；
- `telegram-bot-token`：保存当前活动通道的 API key 或完整 Webhook，权限 `0600`；保留历史文件名以兼容备份与回滚，日志、审计和 API 响应均不包含凭据/chat ID；
- 文件采用同步、原子替换和 Windows 可恢复替换路径；启动时严格 JSON 解码并校验大小、字段和权限。

通知规则 `hostExpiryEnabled` 区分未迁移与显式关闭；首次启动将旧主机提醒配置合并为全局值（任一有效旧开启则开启，否则关闭），原子保存后才运行评估，写失败停止初始化。此后旧逐台标记不控制提醒，旧客户端 PUT 省略新字段时保留当前选择。已有验证渠道发生发送错误时，仍可保存事件规则以关闭提醒；不会清除渠道错误状态，关闭外部推送后重新启用仍须渠道就绪。

PUT、重新发现和测试均经过现有 Session、Origin/CSRF、审计和 `ExpectedResourceVersion` 冲突控制。新凭据
先完成 API 校验/私聊发现或验证消息发送，再写 secret；状态写入失败会恢复旧凭据，如验证消息已投递则错误码显式标记部分成功。服务重启后从告警状态恢复去重，
不会因为重启重复发送同一个 SSH 登录事件。

### 本地记录与外部投递

本地记录不依赖 `enabled`、凭据或渠道健康度；`enabled` 只控制外部推送。规则关闭后不产生该类新事件。

登录后的可见面板每 15 秒读取最新最多 50 条记录，经典与桌面模式共享同一订阅。首次读取只建立事件编号基线，
不会弹出历史消息；之后的新事件以面板内浮层提示，单轮多条合并，并替换上一条未关闭的通知浮层，避免堆叠。
点击「查看通知记录」重新读取通知页；列表按类型直接显示阈值与到达值、恢复当前值、连接状态或 SSH 用户/来源/方式，常见事件在宽屏单行呈现，窄屏与长内容自然换行。未识别的消息保留文本展示；「查看原文」可读取完整消息与投递详情。浮层约 12 秒关闭，完整内容继续保留在本地历史。
后台页和断网页暂停检查，返回时合并提示未见新事件；相同事件编号在当前页面生命周期内不重复提示。
退出登录/进入公开页清除浮层和订阅；会话过期停止检查。临时请求失败安静重试，单次请求最多等待 10 秒。
在线提示不依赖外部渠道，不申请浏览器系统通知权限；各浏览器页面独立维护游标，不提供跨设备已读状态。
事件与评估游标在一次原子文件替换中提交，成功落盘后才发送；发送失败不会阻止记录恢复事件。
投递尝试更新同一事件，不创建重复历史；外部协议无法保证 exactly-once，发送成功但回执落盘前崩溃可能重投。
重试绑定原渠道凭据指纹，关闭推送、关闭规则、移除主机、更换凭据或超过 24 小时后停止投递。
后来接入渠道不会回放 `local_only` 历史。累计流量和 SSH 首次观测/去重语义保持不变。

历史 API 仅供已登录管理员读取，使用服务端时间、主机、类型、性质、投递状态、关键词组合筛选和序号游标分页，
每页默认 50、最多 100 条。字段保持有界，不返回渠道指纹、凭据或平台原始错误。恢复记录关联保留范围内最近告警。
时间持久化为 UTC，列表沿用面板日期格式，消息保留事件产生时的语言和宿主机时区。

首次升级仅导入原告警游标，不伪造旧事件；之后历史文件是评估游标的真源，旧状态文件字段保留作兼容快照。
历史损坏时保留原件、停止记录与投递，并通过配置状态及历史 API 显式报错，修复文件后重启加载；瞬时写失败可在下一轮恢复。
容量和保留期清理在每次评估执行，查询也会排除已过期条目。清理可能移除尚未发出的最早事件，剩余容量有限时以新事件为先。

存储评估：组合筛选触发 SQLite 选型复核。本版保留有界 JSON：最多 2,000 条/4 MiB、每 30 秒评估、每轮批量提交，
没有跨记录业务关系或额外依赖；查询在内存快照有界扫描。增加容量、索引或持续写入频率前须按存储策略重新测量并评估 SQLite。
现有面板迁移备份继续只备份通知设置/凭据，不包含运行历史，与活动审计历史同属本机记录；需要保留历史时应在停止 Panel 后
备份整个 `notifications/` 目录并保持文件权限。恢复整个目录保持事件和游标一致。包含 `hostExpiryEnabled` 的新配置及历史不能由不认识该字段的旧二进制读取；
回退时须停机并恢复升级前对应版本的整个通知目录备份，不能只替换二进制。重新升级应恢复同一新版本的数据快照，不能把旧程序期间的状态当作连续历史。

`scriptLinkageState=not-required`：无需发布脚本（不适用）。候选沿用 Dockerfile 中脚本
`2b90b2d2ca56bc954c9328a51bb5571e896f713d`，SHA-256
`806b4715664fad502f7faeccbc75972f2d1a24559d46208221b98f774ef56c99`；只消费既有集群遥测，不改变 Agent、轻节点或脚本协议。

## 5. 兼容与协议边界

新的 `SSHLogin` 是可选字段，并通过能力头协商：新 v1/v2 控制端声明 `ssh-login-v1` 后，被控端才返回；
旧控制端仍收到旧形状摘要。本机 Panel 到 Agent 也只在带有 `capabilities=ssh-login-v1` 的遥测请求时读取该可选字段，
避免旧 Agent/新 Panel 升级窗口产生严格 JSON 解码冲突。

普通 Agent、轻量节点 root broker 和轻量节点遥测进程共用集群边界中的窄事件读取器。普通 Agent 直接读取
Linux journal，journal 可读但没有 sshd 记录时回退 `/var/log/secure` 或 `/var/log/auth.log`；轻量节点由
`kejilion-node-ssh-login.service` 以 root 读取相同来源，只把严格校验后的单条事件原子写入
`/run/kejilion-node-ssh/ssh-login.json`，非 root 遥测服务继续通过原有 `light-v1` HMAC 上报。
所有通道发送仍只发生在中心端。

新中心在 enrollment 和 report 响应中返回 `X-KPanel-Light-Response-Capabilities: ssh-login-v1`。
新接入节点立即启用；已有轻量节点由现有 root 自动更新任务在下载并校验新版 Agent 时自动安装采集服务，
不需要逐台执行 `k kpanel node update`，也不需要再次配对或消耗一次性授权码。节点配置和 reporting key
保持不变；重启后最多先发送一次旧格式 report，再根据响应头启用 SSH 字段。旧中心不返回响应头时继续发送旧格式，
不会破坏兼容性；若旧中心因严格 JSON 解码拒绝一次带字段 report，节点会自动去掉 SSH 字段重试并回退到旧格式。
第一次看到已有登录记录时只建立基线，不会把历史记录当作新告警。

本阶段实现 Telegram、飞书、钉钉和企业微信四个通道，复用同一套规则、状态机、审计和安全出站边界。为保持最小可回滚变更，
持久化 schema 仍为 v1，历史 `telegram` 状态字段承载当前渠道的通用状态，新 API 另返回 `provider` / `channel`；旧客户端继续获得 Telegram 兼容视图。
上述渠道字段复用只保证渠道迁移本身不新增未知字段，不代表后续通知规则可直接回退。服务器到期全局规则的回退遵守第 4 节的版本备份要求；如恢复的凭据是机器人 Webhook，仅支持 Telegram 的旧版会将其视为无效 token 并停止发送。

## 6. 验收边界

### 本机证书与关键容器提醒（已下线）

`集群 → 通知` 已移除「本机资源提醒」及证书、容器配置展示；暂不迁移到网站或 Docker，
也不新增通知入口。原有集群 CPU、内存、磁盘、流量、累计接收/传送、主机失联、SSH 登录
及 Telegram 接入、测试和发送保持原有行为。

- 即使旧配置已开启，后台也不再采集或评估本机证书/容器提醒，不发送故障、重复、失败重试
  或恢复通知。打开通知配置不再触发本机资源发现，兼容 `resources` 返回空列表和 unknown 状态。
- `rules.resourceAlerts` 及持久告警状态保留，兼容读取原值。保存普通通知设置时保留这些字段；
  直接 API PUT 传入、修改、清空或省略 `resourceAlerts` 均不改变已保存的本机资源规则，不能重新启用。
  暂停时间到期或服务重启也不会恢复执行。无需清空通知目录或迁移用户数据。
- 保留 Agent 既有的鉴权只读资源接口及解析契约，但通知服务不再调用它。下线不改变网站、
  Docker 的正常资源读取和管理能力，也不改集群摘要或轻量节点协议。

`scriptLinkageState=not-required`：本次仅下线 KPanel 提醒，不改变 `kejilion.sh`、证书维护
产物、签发/替换/续签协议或 Docker 生命周期。回滚本次提交会恢复此前提醒行为，保留的已开启
规则和待发送状态可能继续执行；应根据实际需要安排回滚。回退到更早、不认识资源字段的二进制
仍受严格状态解码限制，Git 回退不自动回退运行数据。

定向回归覆盖旧启用配置、持久重试/恢复状态、重启、直接 API 写入、普通通知保存与集群通知发送。
Mock UI 和本地测试接收器均不代表真实 Telegram/飞书/钉钉/企业微信或生产验收。

- L0/L1：类型、能力协商、严格解码、凭据脱敏、官方 URL 白名单、平台请求/响应契约、原子文件、状态机和前端类型/编译测试；
- L2：完整 `go test ./...`、前端构建/检查、`make verify-change` / `make verify-l2` 对应门禁；
- L3：仅在 `arena-154` 验证服务启动、配置目录权限、重启恢复、集群主机状态变化和真实 Agent/轻节点遥测路径；
- 真实发送必须使用用户临时提供的 Bot API key 或机器人 Webhook，验证后立即撤销或轮换，不保存到仓库、终端记录或交付物。

没有真实凭据时，四个平台的 HTTP 交互使用本地假服务或自定义 Transport 覆盖；这不能替代真实平台、真实网络和
真实会话/群机器人验收，最终报告会分别标出两类证据。

## 面板登录通知

集群通知的“事件通知”区域提供默认不勾选的“面板登录”选项，随现有通知设置保存为
`rules.panelLoginEnabled`（false 时不写入状态文件）。勾选后，本 KPanel 每次登录成功都生成一条
`panel-login` 本地记录；外部推送仍由渠道总开关和渠道就绪状态决定。竞品对照：Komari 与 monitor 有同类
登录通知，哪吒没有。

- 触发：`POST /api/v1/auth/login` 与通行密钥登录成功、设置会话 Cookie 并写入审计之后提交；失败、限流、
  需要两步验证的中间步骤和初始化建号都不触发。主机 SSH 登录仍由“SSH 登录”规则负责。
- 内容：主机名、登录时间、用户名、来源 IP（沿用 `remoteIP` 的可信代理规则）、方式（密码、密码 + 两步验证、
  通行密钥、通行密钥 + 两步验证）和发送时间，按保存设置时的语言生成。两步验证依据账户是否启用 TOTP 判断，
  因为登录对启用 TOTP 的账户必须先校验第二因素。不包含密码、验证码、恢复码、会话令牌或浏览器信息。
- 时延与边界：登录请求只把事件放进容量 16 的内存队列后立即返回，队列满时丢弃该条通知而不影响登录。
  通知服务的后台循环取出后与已排队的登录合并为一次原子提交并立即投递，不等待 30 秒评估周期，
  也不推进主机告警的连续计数。本机不在主机列表中（例如列表读取超时）时只记录为待发送，交给下一次评估。
- 失败：投递沿用现有重试、渠道指纹绑定和 24 小时期限；关闭规则后，尚未送达的登录通知停止重试。
  服务停止时队列中尚未提交的通知丢失；已提交的记录保持待发送或失败状态，由重启后的评估继续。
- 回滚：旧程序严格解码 `notification-state.json` 和 `notification-history.json`。规则从未开启时两份文件
  不含新字段；开启过或已有 `panel-login` 记录时，回退前先关闭规则并恢复升级前的通知目录备份，不能只替换二进制。

## 服务检测通知

集群通知的“事件通知”区域提供一个默认不勾选的“服务异常通知”选项，随现有通知设置一起保存。
勾选后自动覆盖本机及所有已接入主机在历史监控中配置的全部 Ping/TCP/HTTP 检测项，新增主机、
新增或修改的检测项自动纳入；不再提供单独页面或逐项订阅。中心现有
`GET/PUT /api/v1/cluster/notifications` 的 `rules.serviceChecksEnabled` 为唯一开关，沿用会话、
CSRF、审计、原子保存和版本冲突保护。默认值为 false。既有渠道总开关和凭据仍为真源。

- 复用 5 分钟检测，源端连续失败 3 次确认异常、成功 2 次确认恢复；中心每 30 秒评估，
  epoch/sequence/checkedAt 防止重复轮询算作新样本。通常 10–15 分钟确认故障，再加上上报和投递时间。
- 主机不可用时暂停服务投递并保留待发送恢复；采样中断超过两个检测周期加一分钟后，每主机
  一条数据中断提醒。unknown 不计成功；明确删除的检测不产生采样中断事件。
- 状态和 outbox 原子保存后才发送。失败按 30/60/120/240/300 秒加 0–10 秒抖动重试；
  每 30 秒最多尝试 8 条消息，同主机合并至 1,800 字节内，暂停事件不占额度。
  恢复早于首次成功发送时合并为“曾异常，现已恢复”，同一故障不循环提醒。
- 每个检测只保留当前事件槽，不累积无限历史；最多 1,616 个检测和 101 个采样状态，文件最多 4 MiB。
  持久化失败不推进内存状态，网络发送不持有状态锁。存储/投递错误与恢复按状态变化写入服务日志，
  固定错误码不含目标或凭据，相同错误不重复刷屏。关闭时不拉取额外遥测，待发送事件会被清理。
- 发送语义为至少一次；渠道已收到、进程在确认落盘前中断时，重启可能重发同一 Event ID。
  修改配置时已在途的一条消息可能完成，后续批次会检查总开关及渠道版本。

独立文件 `notifications/service-check-alerts-v1.json` 仅保存有界事件和待发队列，备份时清空这些运行状态。
开关随 `notification-state.json` 的其他规则保存；备份保留规则偏好但关闭集群通知总开关。
回滚到不支持该规则的旧程序前，先取消勾选并保存，确认状态文件不再含 `serviceChecksEnabled`
（false 使用 omitempty），或恢复升级前配置备份；旧程序严格解码，不能直接读取启用的新字段。
旧程序忽略独立 outbox 文件。改目标会重建对应事件，重命名不改变检测身份。
`service-checks-v1` 可选能力沿既有联邦/轻节点认证上报最多 16 KiB；HTTP 目标仅含 host:port，
不含路径、查询、凭据、响应正文或原始错误。摘要不进入旧集群快照磁盘格式，重启后等待新遥测。

轻节点 root 文件代理写 `/run/kejilion-node-monitoring/check-status.json`，目录 root:kejilion-node 0750、
文件 0640；非 root 上报进程仅接受 root 所有、不可写、无符号链接的有界文件。无新服务或安装协议，
`scriptLinkageState=not-required`。旧节点没有摘要，需要升级节点后才支持服务通知。
中心停机期间不能实时发送，尚未上报且期间已恢复的短故障不能补录。服务 outbox 不等同于通知历史列表；
其他候选增加统一通知历史时须显式接入并核验集成。
