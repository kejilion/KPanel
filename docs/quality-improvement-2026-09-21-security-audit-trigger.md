## 原因假设

- 待验证根因：触发依赖人工记忆和一份会过时的名单，频率要求与发布节奏不匹配，失败状态没有出口。
- 替代解释：审计本身成本太高，无论怎样触发都不会被执行。
- 证伪结果：上线后连续两个稳定版预检都判定需要补审，却都以豁免跳过、没有新的完成 run。
- 涉及 Panel/Agent 权限边界的**审计范围**定义，不改变任何运行时边界或 `kejilion.sh` 契约。

## 产品原则与核心思想对齐

- 业务真源：审计覆盖只从 run 元数据和 Git 历史计算，不另建覆盖状态文件。
- 轻量：稳定版预检多一条秒级命令；多数版本结论为 `ok`，无需任何动作。CI 只增加结构校验。
- 安全：新包默认进入范围，未审计改动最长滞留 14 天，full 最长间隔 30 天，均由机器计算。
- 不引入：入口注册表解析、事后 CI 复算验收记录、L3 编排器改动、新的 JSON 区块。

## 最小改动方案

- 唯一入口：`scripts/check-security-audit-coverage.mjs`（`--validate` / `--require` / `--format=json`）。
- 覆盖链：从最近一次完成的 full 开始，只有完成、`comparison_base` 已被覆盖且 `scope_complete: true` 的 scoped
  才推进；中止或部分 run 如实入库但不计覆盖。run-1 至 run-3 按原文读取。
- 判定：无 full 或 full 超过 30 天 → `full-required`；新边界包或最早未审计提交超过 14 天 → `scoped-required`；否则 `ok`。
  天数按提交时间计算，同一提交结果可复现。
- 豁免：只能由用户明确作出，写入验收记录并带不超过 14 天的补审截止日；豁免不改变检查结论，截止日过后的
  稳定版预检不得再豁免。
- 防止规则自我弱化：非边界包必须写理由且存在。本提案有两处字面放宽，均请复核者判断：
  1. full 频率从"每个稳定版"改为"至多 30 天"；
  2. scoped 触发从"工作项改动触及信任边界包时"改为"出现新边界包，或最早未审计边界提交超过 14 天"。
  依据：两条旧要求在观察期内都没有执行过（v1.20.0 无 full；run-2 之后积压 19 个未审计边界提交无人发起 scoped）。
  新规则把边界范围从 5 个包扩到 `internal/`、`cmd/` 全部包，把未审计滞留上限从"无限"收紧到 14 天，
  且由机器计算，净效果是收紧。
- run-2 按历史 run 视为完整覆盖（推进覆盖链至 `23cbb997`）：它的范围写作"diff 6340e078..23cbb997 security-related
  production paths"，`reviewed_path_count` 为 97，而该区间按新策略有 42 个边界文件；账本未入库，
  这是基于元数据的判断，不是逐文件核对。
